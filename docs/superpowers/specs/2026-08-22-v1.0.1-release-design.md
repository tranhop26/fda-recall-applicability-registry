# v1.0.1 Verified Release Design

## Goal

Publish an immutable `v1.0.1` GitHub release from the final verified `master`
commit, including the secret-free CI quality gate added at
`7f9b0926993a6f2e26e0dd6b922a6e1b1d78dda4` and the approved release
documentation.

The existing `v1.0.0` tag and release remain unchanged so that published
history continues to identify the exact source bundle originally released.

## Scope

The release will:

- create an annotated `v1.0.1` tag at the verified `master` commit;
- build a clean source ZIP from tracked repository files;
- include the verified Studionet deployment manifest as a separate asset;
- publish SHA-256 checksums in the release notes or a checksum asset;
- link the successful GitHub Actions run for the tagged commit;
- download the published assets and verify their digests after publication.

The release will not redeploy the contract, send a transaction, request a
wallet signature, move `v1.0.0`, or introduce new product behavior.

## Release Inputs

- Repository: `tranhop26/fda-recall-applicability-registry`
- Baseline CI commit: `7f9b0926993a6f2e26e0dd6b922a6e1b1d78dda4`
- Source commit: captured from the final synchronized `master` after the
  approved release documentation is committed
- Existing release preserved: `v1.0.0`
- Deployment manifest: `deployments/studionet.json`
- Baseline CI evidence: GitHub Actions run `32554211430`
- Release CI evidence: the successful run for the final source commit

## Packaging and Safety

The source archive will be generated from Git-tracked files at the release
commit. Local outputs, virtual environments, caches, `.env`, credentials and
other untracked files cannot enter the archive. The package will be inspected
before upload for prohibited paths and secret-like filenames.

The deployment manifest will be schema-validated before publication. The
source archive and manifest will each receive a SHA-256 digest. Published
assets will be downloaded into a temporary directory and hashed again; any
mismatch makes the release verification fail.

## Verification Flow

1. Commit and push the approved release documentation, then confirm the
   worktree is clean and local `master` and `origin/master` identify the same
   release-candidate commit.
2. Run formatter, lint, non-live direct tests, integration collection, and JSON
   schema validation.
3. Wait for the release candidate's GitHub Actions run to succeed.
4. Build and inspect the clean source archive, then calculate asset digests.
5. Create and push annotated tag `v1.0.1` without modifying prior tags.
6. Publish the GitHub release and attach the source ZIP, deployment manifest,
   and checksum evidence.
7. Read back the release metadata, download its assets, and verify their
   digests against the locally computed values.

## Success Criteria

- `v1.0.1` resolves exactly to the approved source commit.
- The GitHub release is public, non-draft, and non-prerelease.
- All required assets are downloadable and checksum-verified.
- The package contains no secret or local-only file.
- CI and local quality gates are successful.
- `v1.0.0` remains unchanged at commit
  `7cf03c54e7cae76fc01f75f98bccf01378a7f517`.

## Recovery

All validation and packaging steps occur before publication. If validation
fails, no tag or release is created. After publication, the tag is treated as
immutable; corrections require a new patch version rather than moving the tag.
